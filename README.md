# HEXU · 合序

### 让人和 AI，一起交付。

**AI 研发协作平台 · 从需求到可验证交付**

</div>

---

HEXU 将需求、任务、人员、AI 工具、开发环境、代码变更和验收依据连接起来，让一项研发工作能够跨人、跨工具、跨模型持续推进。

它不是另一个聊天窗口集合，也不是监督开发者的后台。它的目标是：**保留个人使用工具的自由，让团队共享必要的目标、决定、责任和成果。**

> **当前状态：产品规划阶段。** 本仓库已建立完整目标蓝图，尚未实现文档中的产品能力。规划基线为 v1.0，日期为 2026-09-25；这不是软件发布版本，也不是已完成的用户研究结论。

## 产品面向什么问题

| 场景 | HEXU 希望带来的变化 |
| --- | --- |
| 需求散落在聊天和口头安排里 | 从自然语言开始，逐步确认目标、边界和验收方式 |
| 每个人在本地使用不同 AI 工具 | 围绕同一个任务协作，不要求先迁移全部开发环境 |
| 换工具、换模型、换同事时重新解释 | 通过上下文包与代码检查点继续，而非承诺无损迁移模型内部状态 |
| 多人、多 AI 并行但缺少协同 | 明确负责人、依赖、执行范围和需要人决策的事项 |
| AI 说完成，却不知道是否真正交付 | 将产物、验证、人工验收和发布分别记录并关联版本 |

## 完整目标，而不只是首期范围

HEXU 的最终流程是：

**想法进入 → 需求确认 → 任务规划 → 人与 AI 执行 → 集成验证 → 业务验收 → 发布与反馈。**

网页是团队统一入口。本地执行器连接开发者现有环境；远程执行节点作为另一种可选方式。没有现成需求系统、企业内网或统一身份服务，也应能够开始使用。

优先接入 Claude Code 和 Codex，后续通过能力适配扩展工具和模型。具体支持范围、账号授权与平台兼容性必须通过验证，不在此承诺所有组合均可用。

## 六条产品底线

1. 正式团队任务保留明确的人类责任人；AI 可以执行，不能成为责任的替代品。
2. 个人探索可以轻量开始；共享前明确哪些信息将对团队可见。
3. 任务、原生会话、运行、工作区与交付物不是同一个对象。
4. 切换执行者必须检查代码与上下文；改派任务不等于旧进程已经停止。
5. AI 结束、测试通过、人工验收和发布成功是不同事实。
6. 界面准确呈现未知、失败与权限边界，不用漂亮的状态制造虚假确定性。

## 自研与复用立场

HEXU 自主定义产品、领域模型和用户体验；不预设 fork 某个现有平台。可复用成熟基础组件与工具官方接口，但必须核查许可证、依赖、维护成本和具体授权。

本次仅建立产品文档，没有选择软件许可证、没有复制第三方源码、没有修改仓库可见性，也没有接入模型账户或生产环境。许可证选择记录在决策文档中，待仓库所有者确认。
