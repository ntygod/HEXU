# 接受接手与当前操作者

适用：同机 team-local、同项目的 Linux 接收节点。邀请方已明确发布固定副本，接收者已用自己的原身份将该副本恢复到独立目录。收到对象、历史恢复报告、本机新核验、接受接手及开始模型运行是不同事件。

## 网页与本机确认

1. 指定接收者在原任务打开「接手邀请 → 接受接手 → 核对并接受」。核对当前工作说明与讨论；出现变化时需要明确重新比较，不能静默提高修订号。
2. 默认只接受当前操作者职责。仅邀请方提出负责人移交时，接收者可以另行勾选「同时接受负责人职责」；未勾选不会改变负责人。
3. 「开始本机确认」保存独立操作并预约 Task，最长十分钟且不超过邀请/材料期限。此时仍未接受，也没有新 Run；等待期间不能并发创建新的代码执行或接续安排。
4. 在原接收节点，使用原私有状态目录及此前实际恢复的目标目录执行网页给出的命令：

```bash
npm run runner:handoff-accept -- --operation OPERATION_ID --state /path/to/receiver-state --target /path/to/restored-directory
```

终端显示固定邀请、材料与本机目标；输入 `ACCEPT OPERATION_ID` 后重新核对对象库、完整文件清单/字节/模式、目录身份、当前权限及任务上下文。缺少成功恢复、文件被改动/添加、链接/父目录变化、未知写入或日志正被使用时不接受，也不替用户覆盖或清理文件。

成功后 Task 的当前操作者与邀请 accepted、操作 succeeded、历史及 outbox 一起提交。可选负责人移交在同一事务记录改派历史。旧任务的操作者仍保持未知，不从负责人或创建者倒填。当前操作者是协作记录，不授予其他成员的目录、账号或节点使用权。

## 回执、取消与重启

本机核验包在发送前持久保存；回复未知时使用相同命令对账原包。已提交的接手不会重复改派或恢复文件，也不会覆盖随后的人类修改。未确认包保留自己的核验预约与原凭证；不能通过删除凭证或重新配对绕过它。

任务当前编辑者可取消尚未成功的确认。拒绝/撤回/到期邀请会在同一事务取消待确认操作。任务、讨论、权限、材料或写入条件变化会使操作进入需要处理；读取、周期检查和最终提交都会复核。权限恢复、服务重启不会复活旧操作，需重新明确发起。取消不能回滚已经提交的操作者变化，也不停止其他进程或删除文件。

核验使用同 OS 用户的目录预约来排除受管写入。自身只读核验的原预约可在拿到独占日志锁后对账；不会恢复、删除或给其他未知模型进程发信号。对象内容、目录、文件名与凭证不上传，服务只接收有界数量、时间、哈希和不透明目录引用。

文件检查与服务事务不构成跨进程/网络的分布式原子事务，也不隔离同 OS 用户的手动修改。本次提交记录核验时事实，不承诺目录今后持续不变。原恢复目录尚不会因此自动变成已登记的 Git 工作区或模型执行目录；下一步见 [22](../development/22-next-delivery.md)。

## 接口与验证入口

`GET .../handoffs/:handoffId/acceptance-preview` 返回当前版本；`POST .../accept` 返回 202 与持久操作。`GET .../acceptances`、`GET .../acceptances/:acceptanceId` 读取状态，`POST .../:acceptanceId/cancel` 使用独立操作修订和幂等键。

`POST /runner/v1/handoff-acceptance` 仅接受原接收节点 Bearer 渠道的 inspect / commit / 有界失败类别，不接受浏览器 Cookie、路径或执行命令。核验新提交只接受近期匹配证据，旧成功回执仅对账原指纹。固定说明使该专用节点回复上限为64 KiB，其他协议限制不变。

实际检查见 [21](../development/21-implementation-status.md) 与 [本轮记录](../development/history/2026-09-29-handoff-acceptance.md)；工程测试使用真实临时 Git/HTTP/SQLite/目录和虚构凭证，不调用真实模型。
