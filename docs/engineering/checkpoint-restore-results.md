# 本机恢复结果回到任务

HX-DEV-12-02 的恢复结果元数据切片，见 [PR #19](https://github.com/ntygod/HEXU/pull/19)。在已有[本机恢复](checkpoint-restore.md)之上，原节点本人明确发布最后记录，原任务可以查看结果与报告历史。**这是历史观察，不是实时磁盘检测、Handoff 接受、任务完成或模型执行许可。**

## 使用入口

在原节点的 Linux / Node 24 已构建工程执行：

```sh
npm run runner:restore-report -- \
  --state /path/to/private-state \
  --target /original/restore-target
```

`--state` 必须是原配对状态目录；`--target` 是这条恢复记录原来选择的规范绝对路径，不是重新选择一个目录。目标后来被用户移动或编辑时也不会重新访问、写入或恢复它。命令不接受网页计划、原始对象内容或新的运行参数。

新观察需在终端输入 `REPORT <恢复记录ID>`。命令先显示恢复记录身份、恢复/材料/清理状态及公开范围，确认后复核原节点当前权限，再保存待发报告并发送。状态未变化或存在待确认回执时，只对账原报告，不再收集新同意，也不悄悄追加新报告。

在网页原任务进入 **代码检查点 → 核验与本机保留 → 对应对象保留记录 → 查看恢复记录**。每条卡片可展开来源/指纹和分页报告历史；记录与报告每页20条。页面没有目标路径输入、恢复、发布或删除目录的按钮。`runner:restore-status` 仍只读本机记录，恢复/清理也不会自动发布元数据；报告不是它们的额外审批门槛。

## 报告与文件状态

| 显示范围 | 含义与限制 |
| --- | --- |
| 暂存已核验 | 只表示暂存当时通过核验，未发布目标 |
| 文件已发布（本机报告） | 本机已记录发布成功；不证明目录现在存在或未被修改 |
| 取消、失败、中断 | 不被数量达到100%或目标存在自动改为成功；材料位置未知单独显示 |
| 暂存保留、清理中、已清理、需核对 | 只描述本次暂存清理，不表示删除源对象副本或已发布目标 |
| 本机记录时间与服务收到时间 | 两个时间分别显示，不用通信时间伪造文件核验时间 |

新恢复在实际暂存核验通过后记 `verifiedAt`。旧日志没有此字段时公开为 `null`，界面说明“此记录没有单独核验时间”，不倒填历史。最后状态是 `verified`/`publishing` 等非终态的旧进程记录，会在下次独占管理进程取得日志锁时按已有规则记为 `interrupted / unknown`；报告不能复活原进程，也不能在活动写入者持锁时抢先报告。

CLI 返回 `currentFilesVerified:false`、`modelExecutionAuthorized:false`。完整本机计划、目录身份、文件归属和错误正文仍只在私有恢复日志；报告命令不读取输出目录、原仓库或持久对象字节。

## 公开内容与权限

公开内容限定为恢复/原保留/任务/检查点/节点身份、来源提交、计划和快照/报告指纹、数量、时间、恢复/材料/清理状态。**不上传绝对路径、文件名、原始对象字节、凭证、本机目录身份或错误正文。** 指纹用于一致性核对，不是写入或下载令牌；服务端也不能仅凭报告排除恶意节点伪报。

创建每条报告和重放每个旧回执，都重新检查当前原任务/项目访问、原节点所有者与永久节点修订。浏览器 Cookie 和节点 Bearer 通道不能互用；降权、移除或撤销节点后，原凭证不能借已成功回执继续发布。当前有权的任务读者仍可查看历史，并看到原节点已失效的提示。

已经发生的恢复事实不因源对象到期或明确删除而消失：当前身份仍有效时可以补发历史报告，但不获得新的材料读取或恢复权限。源保留到期时间不是输出目录的有效期限；网页关闭、退出或源副本到期均不会删除输出目录。

## 持久回执与断线

私有 `<state>/checkpoint-restores/journal.sqlite` 增加独立 `restore_result_delivery` 表，每条恢复最多一个固定待确认包；沿用独占进程锁和 SQLite FULL 同步。包在发送前保存，网络失败、响应内容不匹配或本机确认写入失败时保留原包。

服务端迁移22增加 `checkpoint_restore_results` 和不可变 `checkpoint_restore_reports`。结果投影、顺序报告及原任务 outbox 在同一事务提交；迁移不会给旧保留记录补造恢复证据。报告必须连续，同序号不同内容、来源/计划/总量替换、进度回退、未知结果升级成功、已清理状态复活均拒绝。

回执区分 `acceptedSequence / acceptedHash` 与 `latest`：前者确认本次原包，后者是当前最新投影。重放旧回执不会把新清理状态倒回旧取消状态，也不会再次执行本机恢复。

例如，取消后的报告已在服务端保存但回执丢失，随后本机明确清理了暂存。第一次重试 report 只确认旧取消报告，返回 `localChangesPending:true`；第二次执行并明确 REPORT 才发送清理结果。不能将两次不同观察合并为一个原请求。没有待发包且本机状态未变化时，重复命令仍复核当前权限并确认原序号，不新增历史。

每份保留材料最多128个恢复身份，每条最多100个报告；1—99用于一般观察，100仅用于 `cleaned`。**报告限额或服务不可达不会阻止本机明确清理**，未送达的清理观察不能伪称网页已经更新。原身份撤销后未确认报告会保留，不用新凭证重发。

## API 与界面异常

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/v1/tasks/:taskId/checkpoints/:checkpointId/retentions/:requestId/restores` | 当前任务权限下读取恢复结果，使用有界 cursor |
| GET | 上述路径加 `/:restoreId/reports` | 同一父范围内读取不可变报告历史 |
| POST | `/runner/v1/checkpoint-restore-report` | 原节点发布严格有界报告，只接受 `requestId, requestHash, restoreId, sequence, report, confirmPublication:true` |

页面显示服务端最后报告，展开期间定时读取元数据，不触发本机扫描。临时错误保留已有结果并可重读；明确权限拒绝清空列表/历史，不保留可操作的旧编辑入口。没有报告时显示“尚无已确认报告”，不推断没有发生恢复或没有文件。
