# 将成果反馈整理为下一轮要求

在真人固定版本反馈下选择「整理为下一轮要求」。页面先核对原版本和节点方案来源，单独展示原反馈，再预填至多2000字符的可编辑要求。成员修改并确认后，仅保存原Task的待选要求；不启动模型，不把原反馈自动当作执行指令。

这项有限入口用于有明确独立节点Run来源的方案成果。普通文字或legacy成果没有可靠方案来源时说明暂不支持，不猜另一条Run或重建队列。原反馈可以是代码位置反馈或它的回复，也可以是同一方案版本的普通文字反馈。

## 原文、编辑内容与来源

NextInput.body是成员明确保存、以后可按原规则编辑的要求；origin另固定原反馈全文（至多12000字符）、哈希、原作者、消息、ResultRevision、原来源Run、方案/组及可选代码锚点。队列修改或撤回保留origin，后来的成果不改挂来源。来源Run不假装是当前最新接续Run。

方案任务输入区的「下一轮要求」仅查看、编辑和撤回本人尚未使用的要求，新建从具体反馈入口整理，并展开原文或返回原版本消息。原文与当前编辑要求分别显示；硬刷新不恢复尚未保存的页面内存草稿，已保存的队列和来源持续保留。

## 在原方案继续时选择

从比较页「从所选版本继续」进入既有配置窗口，再明确勾选本次要求。默认不选择。服务只给出同Task、同方案/组的记录；反馈来源还必须匹配当前选定的固定ResultRevision。不同方案或不同成果版本的要求不能偷带入当前派发。普通节点接续继续拒绝方案Run，也不提供固定方案反馈要求的携带入口，不绕过原绑定。

原队列最多20条待处理，本次最多6条、合计6000字符，完整方案材料仍受20000字符上限保护。窗口预览与实际派发共用正文生成函数：仅带入勾选后的编辑要求和来源标识，不自动复制反馈原文。要求修订、状态或选区变化会使旧确认失效；新保存的要求不自动加入当前命令。

用户仍需确认原节点、目录、模式及执行；确认才创建新Run。原有本人节点授权、所选代码/目录一致性、Task/分支/选择/来源Run修订、干净现场与终止确认保持。此切片不增加等待安排或原生恢复。

## 回执与状态

保存要求和业务回执/outbox同事务，当前Task编辑权限和原来源在旧回执前再核对。未知回复只确认原正文/来源/键，关闭不撤回；降权清除草稿后晚到回执不能恢复。确认旧创建只找回同一条记录，不重新排队或改写后来编辑。

创建方案派发时在同事务核对所选要求的修订/queued状态并绑定新Run；同请求重试不重复绑定。实际节点running报告后才记started，不宣称模型已理解。明确从未许可的取消可按原机制归还queued；未知或已经许可的启动保留绑定，不重放付费执行。

## 实现与范围

GET `/api/v1/results/:resultId/versions/:revisionId/feedback/:messageId/next-input-preview` 返回可用来源或明确原因；POST同路径的`/next-inputs`只接受`{body}`。沿用task_next_inputs，无第二套队列。`workBranch.continueFrom.inputs`是可选明确id/revision列表，未传时保持原接续行为。反馈来源不能由客户端代填。
