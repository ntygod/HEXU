# 任务内接手邀请

当前切片实现明确发布、拒绝、撤回、到期与历史；**接受接手和操作者切换尚未交付**。邀请不停止现有 Run、不改变负责人，也不授予目录、账户或模型权限。当前版本限 team-local 项目可见任务。

## 发布和处理

1. 原发送者在「代码检查点」把固定副本传给同项目另一位成员的 Linux 节点，双方分别本机同意，对方完成接收核验。具体步骤见 [传输](checkpoint-transfer.md)。
2. 打开任务头部「接手邀请 → 准备接手邀请」，选择已接收副本。接收者由该副本确定，不能替换为任意用户。
3. 核对并编辑工作摘要、剩余工作及必要环境说明；不要填写密钥。邀请期限可选 1 / 24 / 72 小时，且不超过原材料期限。点击「发布邀请」固定内容和任务版本。
4. 指定接收者可拒绝，发布者可撤回；双方都必须保有任务编辑权。项目当前只读成员可查看历史。归档项目仍允许这些人类协作动作。

同一传输同时最多有一份待处理邀请。结束后可以重新明确发布，旧邀请仍保留；一个任务最多保留 200 份邀请，列表按 20 条分页。

## 内容、冲突和权限

已发布的说明、接收身份、提交、快照指纹及排除项不会随任务或原材料修改。任务有新版本时提示差异，不能自动重写邀请。材料不可用或授权变化不意味着历史文件已删除；显示最后记录，不探测接收端磁盘。

编辑期间固定任务基线，SSE/轮询不能替换草稿或提高版本。版本冲突需用户比较后明确确认。短暂读取故障保留草稿，明确撤权、切换身份/空间、关闭或刷新丢弃未保存编辑。

回复未知时「确认上次邀请操作」重发完全相同的内容、版本和幂等键。旧回执只确认原动作并返回邀请最新状态，不重复发布或复活已关闭状态。关闭窗口不是撤回已发送请求。

到期由服务周期检查或当前读取落盘，记录系统事件；不派发模型、不清理副本。拒绝/撤回同样只关闭邀请。完整任务访问始终由原权限决定，邀请不创建额外共享授权。

## 当前 API

- `GET /tasks/:taskId/handoffs/options`：原发送者可选择的已确认接收材料。
- `GET/POST /tasks/:taskId/handoffs`：有界列表 / 固定准备完成的材料并发布。
- `GET .../:handoffId` 与 `GET .../:handoffId/history`：当前状态与不可变流转事件。
- `POST .../:handoffId/reject`、`POST .../:handoffId/withdraw`：仅接受 `expectedRevision`，需幂等键。

首版由网页在内存中准备说明，发布请求一次性保存 `offered`，没有持久化的准备草稿或可用的 `accept` 路由。下一步及真正接受所需的现场核验看 [22](../development/22-next-delivery.md)。
