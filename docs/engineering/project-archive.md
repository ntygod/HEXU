# 项目归档、恢复与执行处理

当前交付为同机 preview/team-local 的项目状态功能，不扩大部署或执行授权。归档不是删除，也不是强制冻结人工协作。

## 使用

打开项目右上角“项目设置”，先处理未保存的名称/说明或版本冲突，再展开“查看归档影响”。面板只显示自己当前有权看到的活动执行和待接续数量。明确选择保留已获许可/已启动执行，或同时请求停止有任务操作权的执行，再确认归档。所选策略作用于确认时的状态，包括查看面板后新启动的执行；不会取得私有任务控制权。

归档后，任务、消息、成果、代码与成员访问范围保留，人工讨论、成果发布和完成任务仍按原权限操作。项目列表默认显示当前项目，可切换“已归档”；侧栏、项目与任务页标注归档。活动执行继续显示，停止仍可单独请求。

在设置中点击“恢复项目”只解除对新执行的限制，不重新派发旧工作。未收到回执时使用“再次确认项目状态”复用原请求；关闭抽屉不撤销已经发出的请求。身份/空间/管理权变化会清除旧页面状态，不恢复旧草稿。

## 归档怎样影响执行

| 确认归档时的状态 | 实际处理 |
| --- | --- |
| 尚未获许可的节点派发（queued/accepted） | 取消，阻止一次性启动许可；仅这些确定未启动的所选要求回到待选 |
| 已获许可、运行中、正在停止或未知节点执行 | keep 不替换原状态；stop 仅请求停止当前有任务操作权的运行，等待实际终止证据 |
| preview 排队/准备执行 | 持久取消启动意图，并在异步目录准备后、Codex spawn 前再检查 |
| preview/node 等待接续 Operation | 同一归档事务内转 needs_attention，保留固定材料；立即恢复项目也不复活安排 |
| 已完成的 Run / Operation | 原记录不变；不把任务自动标成完成 |

新普通执行、原生会话恢复、接续创建和最终派发均拒绝 `PROJECT_ARCHIVED`。恢复不重发一次性许可，不清理未知进程锁，也不复活被撤销的节点凭证。保留运行不代表取消原有预算/超时/通信故障停止策略；本功能不承诺离线进程立即收到停止或零额外模型费用。

## API 与存储

`GET /api/v1/projects/:id/activity` 返回当前可见项目的活动运行和待接续数量，遵守私有任务范围。

`POST /api/v1/projects/:id/lifecycle` 归档接受 `{action:"archive", expectedRevision, activeRunAction:"keep"|"stop"}`，恢复接受 `{action:"restore", expectedRevision}`。仅项目管理者可操作（preview 仍是示例身份），需要现有幂等头。拒绝附加命令/路径/权限字段。过期修订返回 409；同状态且当前修订不产生新历史。旧回执仅返回已提交结果，不再次选择/停止后来产生的执行；随后读取当前项目以确认最新状态。

迁移 10 为现有 project_revisions 增加归档时间和操作者字段；旧项目未记录字段视为未归档，未知历史保持 null。状态/修订、Operation 暂停、未许可派发取消、outbox 和回执共同提交或回滚，保留原项目/任务/执行 ID。归档只取消执行意图，不对 Git 执行 reset/stash/commit/push。

## 验证边界

工程检查覆盖实际 SQLite/HTTP/子进程生命周期，原生执行使用明确协议替身和虚构 Key，不代表真实 Claude/Codex 账户生成或恢复已联调。浏览器、工程检查结果及实际平台见 [实现进度](../development/21-implementation-status.md)。远程部署、Windows 原生进程和跨电脑归档传播未交付；macOS 未实测。
