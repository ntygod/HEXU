## 1. 适用场景

同机换工具主要用 11，不强制生成正式 Handoff。本包用于别人接着做、换电脑继续、个人工作公开给团队，以及发布有限范围材料。默认先由系统准备，用户只处理真实缺失项。

## 2. 检查点的两种实现

**Git 提交引用：**记录每个仓库的 remote identity、commit、分支说明和可访问性。跨仓库任务使用仓库/commit 集合，不用一个字符串代表所有代码。未推送提交必须明确本地可用范围。

**基线加补丁包：**记录 base commit、已跟踪差异、选中的未跟踪文件、文件清单、大小/哈希、必要环境说明和排除项。二进制用实际 blob；LFS/submodule 按可获取引用处理，不假装指针是完整内容。默认排除凭证与私有环境文件，用户看到遗漏说明。

捕获时确认现场一致：活动写入先停止，或选择已知不可变的提交；不能边复制变化中的文件边声称拿到一致快照。每份 bundle 完成后才发布，上传中断可续传，服务在校验完整清单前不标记 ready。

## 3. 接手流程

来源用户选择接收者和可选目标节点，系统生成摘要与检查点；发布 offered 后，接收者点击接手。服务检查任务访问权/接手授权，执行器核对目标仓库、基线、磁盘和工具等必要条件。

恢复到新的目录或明确可覆盖的干净现场，不对已有个人改动执行 reset --hard。应用失败保留源检查点和错误，新目录标记恢复未完成；部分成功不更新主任务操作者。

恢复完成且写入冲突已排除后，通过 expectedRevision 原子写 accepted 与 operatorUserId。需要移交负责人时，在同一面板明确选择并由接收方接受；不能从“看看代码”推断接受全部责任。accepted 不是已经启动新的 Run。

原电脑离线且无法确认写入结束，不伪装进程已经迁移。允许另开独立副本探索时，明确这是快照分支而非接管原现场，旧 Run 继续展示未知；是否后续接管由状态核对决定。

## 4. 权限与材料分享

Handoff 不携带模型账号、仓库 token、生产凭证或整个 HOME。接收者使用自己的已授权配置。缺少环境变量只展示键名和用途，不显示源值。

AccessGrant 指向具体快照、接收者、可用操作与期限。分享预览会列出将公开的摘要、文件和选定消息；原记录权限不能仅因被摘要引用就扩大。任务/项目权限、快照权限、节点使用权分别处理。

同空间个人任务转团队时可保留 Task ID，但选定材料之外的私人消息和原生会话仍按原访问范围保护；列表、搜索和事件均需过滤。跨空间发布建议明确创建新的团队工作副本，保留仅原作者可见的来源关联，原个人记录不进行双向状态同步。此建议见 DD-07，不宣称发生了透明跨空间搬迁。

这不是两个 AI 任务系统：一个团队工作仍只有一个权威 Task；跨空间发布是一项明确复制动作。不要在执行器私自把旧 spaceId 改成新值而泄露整段历史。

## 5. 状态与 API

Handoff 使用 preparing/offered/accepted/rejected/withdrawn/expired。`POST /tasks/:taskId/handoffs` 准备；`POST /handoffs/:handoffId/offer` 发布；`POST /handoffs/:handoffId/accept` 开始自动恢复与接手；返回 operationId 并可查询。reject/withdraw 是独立命令。

在核对和接手之间 Task、权限或检查点改变时重新读取必要信息，不能使用过期预检缓存直接接受。重复点击通过幂等键返回同一操作，失败后重试不产生一堆重复目录。

## 7. 技术注意

解包限制相对路径、大小、文件数量与符号链接目标，拒绝路径穿越；临时包加密/访问控制与生命周期由存储实现。检查点文件是恢复材料，不是质量证据，不引入验收审批。

源工作未完成可以交接，接收方不需要先提交测试报告；必须解决的是“拿到的是什么、能否继续、谁能操作”。
