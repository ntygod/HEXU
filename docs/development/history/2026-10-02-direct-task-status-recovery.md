## 原直接路径的诊断

入口包括项目看板的进行中/待处理/已完成状态选择，以及任务详情和固定成果的重开/无活动完成按钮。检查父树实际 `perform`、`changeStatus` 与 client `request` 源函数，通过 AST 提取未改动的函数体，使用注入的引用/内存容器及真实可丢弃 HTTP 服务，覆盖三动作各三类故障，共 9 例。该诊断使用真实请求与业务事务，但没有运行 React 渲染或浏览器事件。

| 故障边界 | 原路径实际表现 | 正确的证据解释 |
| --- | --- | --- |
| POST 未到服务即失败 | 没有保存 pending packet，下一次点击使用新幂等键 | 不能确认原请求；新点击不是对原键的确认 |
| POST 已提交，回包丢失 | 下一次点击换键；仍用旧修订时返回 409，原业务效果只有一次 | 未证明重复已提交业务写入；旧原键重放返回 200 和同一回执，不增加效果 |
| 有效成功 ACK 后 Workbench GET 失败 | 原直接路径未保留 accepted outcome，下一次点击再次发新键 POST；旧修订重试返回 409 | 已接受的业务操作应只 GET 对账，不能把 GET 故障当作需要再写 |

原 catch 只补一次 GET，没有自动 POST 重试；表中的新 POST 来自用户随后再次点击。

另外 3 例分别在请求未发送后，仅更新 Task 标题，再读取当前 Workbench、点击同一动作。每例都改用新键及新 expectedRevision，实际成为新操作；这与“确认原请求结果”不同。诊断确认的是原直接路径的恢复缺口，不描述成重复已落库业务变更，也不归因于 PR56 移植回归。

## 实现边界

只在已有 `apps/web/src/state.tsx` Provider 内扩展原包/会话的动作类型与标签、目标状态核对和直接恢复展示，没有新纯辅助模块。直接操作沿用原 `{ expectedRevision, activeRunAction: 'stop' }` 正文和首次生成的 UUID，在第一次 POST 前保存不可变原 Task、动作、路径、正文及键。

- 未知结果保留原包；后来的标题、修订或其他状态入口不能换包换键。“确认原请求结果”明确重试同一请求；首次发送不弹确认窗，恢复无新的停止选择。
- ACK 必须匹配原 Task ID、目标状态和原修订加一；有效 ACK 后 GET 故障保留 accepted outcome，“刷新任务状态”只 GET。当前投影/SSE 不代替原 ACK。
- 同 Task 进行中原包阻止重复发送。直接首 POST 隐藏时仍可导航；pathname/search 变化使旧 UI/所属读取失效，hash 锚点不触发该分离。关闭或路由变化不撤回原包；另一 Task 会话打开后，旧有效 ACK 只能更新仍属于自己的包，不能刷新或改变新会话。
- 当前不可见/不可编辑、明确访问拒绝与身份/空间变化清除原包；重授不复活。直接请求的明确 4xx 拒绝结束原包并刷新当前状态；未知结果保留。硬刷新不持久化。
- 已有活动完成/取消确认继续保留固定修订和 stop/keep 语义。直接无活动完成保留原停止处理正文，停止请求仍不等于终止；不更改 Run、Operation 或锁语义。

没有后端、schema/迁移、回执 API、完成记录列表或其他旧堆叠功能。[问题52](https://github.com/ntygod/HEXU/issues/52) 和原生/文件/私有材料/registry 审阅保持暂停；本轮不恢复审计、不合并或部署。
