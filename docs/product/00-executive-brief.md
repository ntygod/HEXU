# HEXU · 合序｜管理层产品概要

> 规划基线 v1.0 · 2026-09-25 · 完整产品目标，尚未实现。  
> [返回入口](../../README.md) · [总体产品规划](01-product-plan.md) · [关键界面设计](04-ux-and-design.md)

## 一句话定位

**HEXU 是以人为核心的 AI 研发协作平台，让分散在不同成员、AI 工具和开发环境中的工作，形成可追溯、可接手、可验收的团队交付。**

品牌：**HEXU · 合序**。标语：**让人和 AI，一起交付。**

“合”代表人与工具的协作，“序”代表目标、决策、执行和成果之间的连续关系。不是要求所有人使用同一个模型，而是让不同能力可以有序配合。

## 为什么建设

我们选择解决一个明确问题：个人与 AI 的协作可能很顺畅，但任务一旦跨成员、跨工具或进入团队验收，背景、决定、代码状态和责任往往没有一起流转。

HEXU 以这一问题作为待验证的产品假设，不把“所有团队都因 AI 变得更混乱”当作研究事实，也不提前承诺效率提升倍数。

目标团队可以没有成熟的需求系统和内网。产品应从简单入口开始，帮助形成必要的协作习惯，而不是要求先完成流程改革才能使用。

## 建成后的完整体验

业务同事输入一个想法，HEXU 帮助整理成需求，并把不确定之处交给合适的人确认。负责人把工作拆成任务，成员在本地或远程环境使用 Claude Code、Codex 等工具执行。

当工作需要换工具或换同事时，系统提供当前代码检查点、已确认决定、未解决问题与验证结果。接手者检查后继续，不依赖原负责人重新讲述全部经过。

实现完成后，系统提供代码审阅、功能预览、测试与验收页面。管理者可以从项目目标进入具体成果，知道哪些已验收、哪些待决策、哪些有风险。

**管理者和开发者看到不同视图，但基于同一套任务和交付事实。**

## 四类价值

| 面向谁 | 产品要带来的改变 | 可观察的证据 |
| --- | --- | --- |
| 管理者 | 少靠追问拼进度，能直接查看目标、阻塞和成果 | 能从风险进入原因，从交付进入实际产物 |
| 负责人 | 分工、依赖、交接与验收有共同记录 | 责任清楚，阻塞有人处理，需求变更有人确认 |
| 开发者 | 保留工具选择，减少背景重讲和重复探索 | 跨工具、跨成员恢复工作的人工成本下降 |
| 需求与验收人员 | 不读终端也能提出要求和检查成果 | 验收项、功能预览、问题反馈与版本关联 |

目标是提高交付可预测性并减少协作浪费，不以代码行数、在线时间或 token 数量评价员工。

## 最终产品包括什么

**需求与任务。**内置轻量需求入口、版本、项目、负责人、依赖和里程碑；已有系统可后续接入。

**研发工作台。**任务上下文、原生 AI 工具、模型配置、代码变更、终端、预览与验证集中在同一工作页面。

**团队与 AI 协作。**支持个人探索、团队任务、工具接力、独立复核、并行探索与经授权的自动执行。

**知识与交付。**共享有效的项目规则与决策；把验收依据、发布结果和反馈关联到具体版本。

**运行与管理。**提供本地／远程执行节点、权限、故障恢复、成本记录和面向管理者的真实状态视图。

这些是完整目标，不是要求一次性做完的首期清单。

## 产品第一眼应该是什么样

不是一个黑色终端墙，也不是充满机器人头像的监控大屏。

首页突出正在推进的目标、需要人决定的事项和可查看的交付成果。任务页把 AI 协作、代码变化和真实功能组织在一起。验收页让非开发者直接检查结果。

默认视觉方向是专业、明亮、克制；开发工作区提供深色模式。UI 与异常状态设计从最初就进入验收，不放到项目尾声补做。

建议的演示主线只有一条：**提出需求 → 两人使用不同工具协作 → 中途接手 → 查看功能 → 验收交付。**不靠虚构效率统计或预录日志伪装实际运行。

## 自研边界与投入

自主建设领域模型、协作规则、交接与验收，以及统一体验；复用 Git、成熟界面组件、数据库和 AI 工具官方能力。不重新训练模型，不重做完整 IDE，也不把多个现成平台硬拼成一套系统。

“自研”不等于没有成本。需要分别预算产品设计、研发与测试、服务器与存储、模型调用、日常运维及工具版本兼容。当前没有团队人力和历史数据，不给出缺少依据的总工期、覆盖率或节省比例。

## 关键边界

人类负责人不会因把任务交给 AI 而消失。共享任务不会自动公开所有个人会话。连接成员电脑不会自动赋予管理员任意执行权。AI 输出不会自动成为需求或正式决定。运行结束、测试通过、验收与上线分别记录。

允许有边界的自动化，但高风险操作、范围变化和正式验收必须由有权的人或明确的已批准策略处理；没有策略时默认不放行。

## 建设方式与最终验收

按“体验样板 → 单任务真实执行 → 跨工具与多人协作 → 完整交付 → 可运营扩展”逐步建设，每阶段都向同一个最终目标积累，不先做孤立个人工具再另造团队平台。

最终至少要证明：没有外部需求系统也能开始；两个真人在不同电脑上能协作；Claude Code 与 Codex 能在同一任务中接力；需求变更能影响相关工作与验收；故障不制造虚假完成；管理者能直接找到实际成果。

**HEXU 最终交付的不是一个工具集合，而是团队能够依赖的研发工作方式。**
