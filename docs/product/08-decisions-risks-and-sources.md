## 1. 决策口径

“已明确”来自产品发起者的要求；“本轮规划”是据此形成的设计基线，并不宣称每个实现细节都已单独审批；“待选择”由团队在实现时决定。

## 3. 产品取舍

| 要强化 | 要收敛 | 要保留的边界 |
| --- | --- | --- |
| 从一个问题快速开始 | 创建时的大量必填项 | 归属与权限清楚 |
| 换工具继续、请人或 AI 协助 | 每次切换都走正式交接 | 原写入停止或隔离、缺材料明确 |
| 并行方案的比较与选择 | 同时运行更多 Agent 的展示 | 工作区独立、费用和操作后果可见 |
| 同任务中的上下文与团队约定 | 全量聊天堆进知识库 | 来源、版本和分享范围明确 |
| 成果展示与直接反馈 | 默认验收中心与证据链 | 不伪造测试、运行与发布结果 |
| 老板和开发者的同源视图 | 汇报专用数据与员工排名 | 区分任务完成、执行结束和已发布 |

## 4. 尚需团队选择的信息

实际人数、目标操作系统、现有 Git 平台、账号认证方式、技术栈、服务器和预算会影响实施，不影响完整目标的表达。

实施中只在相关动作前确定必要信息：接入工具时明确许可与身份，开发执行器时明确系统支持，部署时明确网络与数据范围。不要把全部组织决策先转成产品用户的配置向导。

质量标准、效果评估和内部检查由团队维护，不再在产品规划中规定统一样本、周期、指标目标或验收委员会。

## 5. 需要防止的产品偏移

**过度管理：**新增一个表单前，先说明它解决哪种实际协作问题。不要以减少不确定性为由让所有任务变重。

**只做工具壳：**工具接入必须回到同一任务、工作现场与成果，否则仍由用户复制背景。

**协助变成接管：**临时问问题不应改变负责人或给另一个 Agent 活动目录写入权。

**轻量变成不真实：**不强制质量验证，也不能把失联显示为已停止，把旧检查显示为新版本通过。

**视觉与使用脱节：**日常首页不能停留在宣传页，任务页不能只展示聊天，成果页不能只剩状态数字。

**平台拼接与范围扩张：**避免多套任务库、完整 IDE、模型训练、通用办公与复杂流程编排成为默认建设范围。

## 6. 项目管理与产品设计依据

以下原始资料于 2026-09-25 重新查阅，兼顾成熟方法与近期研究。右列为 HEXU 的设计推论，不是资料原文对本产品的推荐。采用方法中的有用原则，不把方法本身做成用户必须遵守的流程。

| 编号与原始资料 | 资料要点 | HEXU 的应用与不采用内容 |
| --- | --- | --- |
| T01 · [Shape Up：Set Boundaries](https://basecamp.com/shapeup/1.2-chapter-03) | 先界定问题与投入边界，避免无边界的功能集合 | 按明确工作切片建设；不强制六周周期、固定岗位或完整 Shape Up 制度 |
| T02 · [The Kanban Guide，2025.5](https://kanbanguides.org/the-kanban-guide/2025.5/) | 关注工作从开始到结束的流动及在制工作 | 突出进行中、等待与阻塞，提供可选并发提示；不建设强制工时和人员产能排名 |
| T03 · [Microsoft Research：Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/) | 人机交互需要考虑能力理解、调用、纠正与持续使用 | 用户能局部编辑建议、拒绝帮助、继续和停止；不把人在环中简化成审批按钮 |
| T04 · [Nielsen Norman Group：Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/) | 优先展示重要操作，高级与低频功能放在可发现的次级位置 | 简短任务入口、按需上下文与资源设置；不删除用户真正需要的高级能力 |
| T05 · [Product Talk：Opportunity Solution Trees](https://www.producttalk.org/opportunity-solution-trees/) | 区分期望结果、用户机会与具体解决方案 | 用减少重复解释、追问和找成果约束功能；不把机会树和实验管理开发成新模块 |
| T06 · [DORA：State of AI-assisted Software Development 2025](https://dora.dev/research/2025/dora-report/) | AI 的影响与组织既有工作系统相关，不只由工具决定 | 重视协作连续性；不据此承诺公司效率提升或要求引入完整度量系统 |

这些资料不构成对公司现状的实地调查。具体效果由内部团队判断，规划中不使用未经测量的提升倍数或成本节约比例。

## 7. 官方技术依据

以下页面于 2026-09-25 重新查阅，用于确认接入方向，不表示已经完成兼容测试；开发时仍以所选工具版本为准。

### S01｜Claude Code 程序化调用

[Run Claude Code programmatically](https://code.claude.com/docs/en/headless) 提供程序化与结构化输出相关说明。产品使用原生事件与恢复能力，不依赖界面文字抓取；费用报告需区分估算、累计与实际账单语义。

### S02｜Claude Agent SDK

[Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) 说明 SDK 的执行与上下文能力，并包含认证限制。技术可调用不等于可将个人订阅封装成共享服务；按具体 CLI／SDK 接入方式核对，不建立默认订阅共享池。

### S03｜权限

[Configure permissions](https://code.claude.com/docs/en/agent-sdk/permissions) 说明模式、规则和回调等权限机制。不能因为有一个网页授权按钮就认为所有原生操作均受它控制；产品应按实际能力显示与执行。

### S04｜Codex App Server

[官方入口](https://developers.openai.com/codex/app-server) 本次跳转至 [ChatGPT Learn 的 App Server 文档](https://learn.chatgpt.com/docs/app-server)。其中的线程、执行事件、授权与实验性能力说明为适配设计提供依据。原生会话、HEXU Run 和节点授权分别管理。

### S05｜Git worktree

[git-worktree 文档](https://git-scm.com/docs/git-worktree) 支持多工作目录的实现思路；它本身不证明文件、数据库、网络与凭证完全隔离。代码版本由 Git 管理，HEXU 不重建版本控制。
