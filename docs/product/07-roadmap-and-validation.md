# 07｜路线图、验证与成功指标

> 规划基线 v1.0 · 2026-09-25 · 最终目标不变，按可验证结果分阶段实施。所有测试目前均未执行。  
> [返回入口](../../README.md) · [完整功能](03-functional-specification.md) · [UI 目标](04-ux-and-design.md) · [决策与风险](08-decisions-risks-and-sources.md)

## 1. 实施原则

不先做一个孤立个人工具，再重新设计团队平台。任务、真人责任、执行与验收从第一条真实流程就使用统一模型。

不把“技术能运行”和“产品能使用”分开验收。每阶段都包含必要界面、权限、失败状态与真实用户流程。

不在没有人力、技术栈、操作系统和模型授权信息时承诺总工期。以下是依赖与验收顺序，不是日期排期。各阶段可以交叉开展，但不得跳过安全和可靠性准入。

## 2. 完整目标的阶段路线

| 阶段 | 交付目标 | 核心内容 | 进入下一阶段的依据 |
| --- | --- | --- | --- |
| M0｜产品与体验基线 | 对最终体验与状态规则达成一致 | 本文档集、主要页面原型、术语与权限规则、技术实验计划 | 关键用户能走通需求、交接和验收原型；未知决策明确 |
| M1｜一条真实任务流程 | 从一个任务进入真实受管执行并看到结果 | 账号项目、轻量需求、任务、一个工具适配、工作区、授权、停止、证据雏形 | 正常与失败路径均可解释；无越权与虚假完成 |
| M2｜跨工具与真人协作 | 两人、两台电脑、两种工具可靠接手 | Claude Code／Codex、能力发现、检查点、上下文包、交接、写入约束、依赖提醒 | 接力和接手的人工成本可测；断线与拒绝场景通过 |
| M3｜需求到正式交付 | 管理者与业务人员进入同一流程 | 需求版本、决定影响、验证、预览、验收、发布记录、管理视图 | 完整需求可追溯到有效验收与发布，不需另填汇报数据 |
| M4｜可运营与扩展 | 能作为团队日常工作基础 | 远程节点、有界 AI 工作流、知识模板、成本、扩展、备份恢复与性能 | 可靠性、维护、权限与采用指标达到批准目标 |

M0 的文档已建立，但高保真原型、用户验证和技术实验尚未完成，因此不能把 M0 宣称已经全部验收。

M1 可先接通一个工具，是降低单次实现风险，不代表最终取消第二个工具或团队能力。用户看到的产品定位始终是完整协作平台。

## 4. 开发工作流与可并行工作

产品／设计维护需求、角色、文案和界面；控制服务维护任务、权限和事件；执行器与适配器维护工作区及原生工具；测试维护契约、端到端与故障注入。角色可由同一人兼任，不在此假设团队已有特定岗位。

首先确定领域字段、状态转换、错误与事件契约，再使用模拟适配器开发界面与服务。模拟器必须能产生成功、失败、等待、取消、失联和过期证据；界面明确模拟标识。

随后用真实工具替换，验证契约差异。发现原生能力不支持时回写产品降级，不在适配层静默伪造。

每条业务切片包含界面、服务、执行器、测试与文档更新。跨层契约变化先确认影响，避免多位开发者及其 AI 同时基于不同假设工作。

## 5. 完整验收矩阵

统一前提：测试仓库与演示数据；至少两个独立用户；至少两个独立执行环境；获准的模型配置。没有这些条件的测试只能标为未验证或模拟通过，不能算真实通过。

| 编号 | 场景与操作 | 必须满足的结果 | 关联功能 |
| --- | --- | --- | --- |
| HX-AT01 | 不接外部需求系统，创建团队、项目与需求 | 可以开始讨论和规划；执行前引导必要仓库与环境 | F01、F02 |
| HX-AT02 | AI 在需求中补充未提出的字段和行为 | 补充内容保持建议，只有确认人能发布正式版本 | F02 |
| HX-AT03 | 修改已确认的接口约定，同时有依赖任务运行 | 相关任务收到影响提示，记录确认与上下文版本；旧证据需复核 | F02、F03、F06、F08 |
| HX-AT04 | 执行退出正常，但未运行测试 | 显示执行结束和验证未执行，不直接显示任务已验收 | F04、F09 |
| HX-AT05 | 同工具恢复；再选择不支持恢复的配置 | 有效会话可继续；不支持时明确新会话与缺失内容 | F05 |
| HX-AT06 | Claude Code 未完成任务交给 Codex，包含未提交变更 | 先处理停止与检查点；新执行有明确输入版本，不靠摘要假装接力 | F05、F06 |
| HX-AT07 | 甲交给乙，乙缺仓库权限或环境变量 | 保持待接手并说明缺失，不继承甲的凭证或自动转移责任 | F06、F11 |
| HX-AT08 | 两个请求同时要求写同一工作区；旧节点随后失联 | 只允许一个受管写入；无法确认旧进程停止时不直接接管现场 | F03、F06、F11 |
| HX-AT09 | 拒绝授权；批准请求过期、动作改变或已被使用 | 真实操作不能执行，旧批准不可重用 | F07、F11 |
| HX-AT10 | 用户访问无权项目，或成员被移除后继续操作 | 读写、搜索、执行与新派发受阻；运行中任务处理范围清楚 | F01、F11 |
| HX-AT11 | 测试与验收通过后，再修改代码或需求 | 历史记录保留，当前证据标记需复核，不计作当前有效交付 | F09 |
| HX-AT12 | 非开发者查看预览、退回、接受并批准发布 | 能理解验收项；验收与发布分开；预览不泄露平台身份 | F09 |
| HX-AT13 | 外部部署超时，网络断开并重放派发事件 | 先核对真实结果，不重复执行副作用；状态未知准确 | F07、F09、F11 |
| HX-AT14 | 原生会话恢复后返回累计费用，或工具无法提供费用 | 按来源去重，区分估算与账单；缺失显示未知而非零 | F05、F10 |
| HX-AT15 | 多条同因阻塞提醒，或向外部渠道发送任务通知 | 正确路由并去重；只发允许范围内的摘要 | F10、F12 |
| HX-AT16 | 节点缺工具、版本不兼容或操作系统未经验证 | 显示明确不支持／未验证，不能假装接入完成 | F01、F11 |
| HX-AT17 | 私有探索转团队，并搜索、导出或生成摘要 | 用户预览共享范围；私有记录和无权来源不被扩大公开 | F04、F08、F12 |
| HX-AT18 | 同一外部 Webhook 重复或乱序到达 | 去重并保持正确版本，不重复建任务或覆盖更新状态 | F12 |
| HX-AT19 | 仓库、网页或其他 Agent 要求绕过规则或读取秘密 | 内容不会成为授权；文件、网络与凭证边界实际生效 | F08、F11、F12 |
| HX-AT20 | 首次用户与键盘用户完成需求、交接和验收流程 | 主要操作可发现，状态无歧义，布局可用且无键盘陷阱 | F04、F10 及 UI |
| HX-AT21 | 从备份恢复数据库与产物，回滚平台版本 | 关键关联可核对；无丢失授权边界；恢复结果有记录 | F11 |
| HX-AT22 | 多 Agent 流程循环、分歧、超预算或持续失败 | 达到边界停止并交人处理，不无限派发或自动扩权 | F07 |

每个测试记录环境、工具与适配器版本、前提、步骤、实际结果、证据和结论。当前结论一律为“未执行”；不存在以文档设计代替运行验证的通过项。

## 6. 用户价值验证

### 6.1 观察真实损失

选择同类真实需求，观察现有方式与 HEXU 方式下需求澄清、工具切换、跨人接手、等待与验收。不能只和“完全没有任何协作”比较，应包含团队现在使用的聊天、Git、说明文档等办法。

记录实际操作而非仅询问功能偏好。探索失败与中断任务也纳入，不只挑成功案例。

### 6.2 建议的试点范围

可从一个项目、三到五位参与者开始，覆盖需求、两个不同工具的开发者与验收角色。数字是建议规模，不是已知公司人数或必须新增的人力。

试点用于验证完整链路的风险，不将产品愿景缩减为只有试点功能。范围扩大前先解决数据越权、重复副作用、错误交接和虚假验收等问题。

### 6.3 避免把统计误认为因果

记录任务类型、范围、复杂度、工具版本与团队熟练度。没有可比较样本时报告观察，不宣称 HEXU 导致效率提升。

试点结果包括没改善、增加负担和放弃使用的原因。不能把“安装了”“登录了”当作持续采用。

## 7. 成功指标与口径

**主要结果：按需求版本统计的有效验收交付，以及达到相同质量要求所需的周期和协作成本。**不以拆出更多子任务提高成绩。

| 指标 | 定义与观察方式 | 防止误用 |
| --- | --- | --- |
| 有效验收交付数 | 统计期内被有权人员接受、证据与当前目标版本一致的需求结果，按需求版本去重 | 任务拆分、重新运行或模型回复不增加交付数 |
| 交付周期 | 可比较需求从正式确认到有效验收的耗时；中位数与较慢分位并看 | 分开报告等待、执行与范围变化；不承诺因果 |
| 交接人工成本 | 准备材料时间与接手者恢复有效工作的人工时间分别记录 | 不只统计点击交接按钮到结束的系统时间 |
| 协作返工 | 因过期决定、错误检查点、权限／环境遗漏等造成的返工事件与耗时 | 原因需人工核对，不让 AI 自动归责个人 |
| 等待决策时间 | 需要处理事项创建到有效决定的时间，按类型统计 | 不鼓励为了速度批量无脑批准 |
| 验证覆盖 | 适用的必要验收项中，存在当前有效证据的比例 | 未执行不计通过；不适用须有理由 |
| 交付后缺陷 | 约定观察窗内与交付相关的问题和严重程度 | 保留报告窗与样本，避免只看上线当天 |
| 平台负担 | 因平台额外产生的填表、切换、故障和维护时间 | 节省时间必须扣除新增负担 |
| 任务成本 | 可获得的模型、执行资源和人工维护投入，按来源区分 | 估算不等于账单，不据此给员工排名 |
| 持续采用 | 在具备适用任务的参与者中，真实持续使用及退出原因 | 不用在线时间或被动打开率替代价值 |

目标值应在取得基线后由项目负责人确认。没有基线时仅收集数据，不提前承诺几倍效率或替代多少人员。

## 8. 候选非功能目标

以下是用于容量与体验验证的起点，需要结合预算批准，不是当前能力声明或服务等级承诺。

| 维度 | 候选目标 | 测量前提 |
| --- | --- | --- |
| 首个容量包 | 20 名成员、10 个并发受管 Run、约 10,000 条任务 | 模型推理与执行节点资源另计，数据库与事件负载按真实样本 |
| 常用页面 | 常规网络下主要可交互内容 P95 小于 2 秒 | 不含外部模型生成与首次代码克隆；固定测试设备与数据量 |
| 事件可见延迟 | 节点事件发出至用户界面展示 P95 小于 2 秒 | 节点在线、服务正常，记录网络边界 |
| 心跳与失联提示 | 候选心跳约 10 秒，约 30 秒无确认后显示状态未知 | 只改变观测状态，不直接证明进程停止 |
| 备份恢复 | 候选 RPO 不超过 24 小时、RTO 不超过 4 小时 | 必须涵盖数据库与产物，通过恢复演练后才承诺 |
| 安全 | 禁止跨项目越权、旧授权重放及无提示重复发布 | 作为上线阻断项，不以平均成功率豁免 |

若预算和网络不支持目标，应调整并解释，而不是通过隐藏慢请求、丢弃异常任务美化统计。

## 9. 上线与扩大使用的阻断项

存在以下任意问题，不进入正式团队使用：跨项目数据泄露；拒绝授权后仍执行；旧 Run 与新 Run 同现场冲突且平台无提示；交接缺代码却标成功；未验收即算交付；外部操作被重复执行；无法恢复重要记录。

关键路径存在未验证工具版本时，不标记正式支持。可先作为受限试验能力，并在 UI 明确风险、范围与退出方式。

## 10. 资源与成本规划

投入按产品与设计、前后端、执行器与工具适配、测试安全、运维支持分别估算。团队小可兼任，但每条关键责任需要有人承担。

模型费用、服务器、存储、出站流量、域名、备份与工具维护单列。免费开源组件不代表整体零成本；减少采购不应转化为无法持续维护的自研范围。

首轮技术验证后再估算工作量：用可交付切片、依赖、未知风险与实际团队吞吐排期，不以代码生成速度作为唯一依据。

## 11. 文档与实现完成定义

需求变化必须更新受影响旅程、功能、状态、界面与验收。关键决策在 08 留下来源与状态。

每个阶段交付应附：可演示流程、真实与模拟能力区别、已通过测试、已知限制、安全与恢复说明，以及下一阶段仍未解决的风险。

**完整产品完成不是 M1 跑通一个 Agent，而是上述跨人、跨工具、从需求到有效交付的场景能够可靠运行。**
