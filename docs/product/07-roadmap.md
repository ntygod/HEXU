# 07｜产品建设路线

> 规划基线 v1.1 · 2026-09-25 · 完整目标的建设顺序，不是工期承诺或已实现能力。  
> [返回入口](../../README.md) · [完整功能](03-functional-specification.md) · [UI 设计](04-ux-and-design.md)

## 1. 建设原则

产品目标始终是：轻量组织工作，支持人和不同 AI 工具持续协作，让成果直观可见。分阶段建设不把最终目标缩成一个多终端启动器。

从开始就使用统一任务、真人负责人、执行记录和成果关系，不先做孤立个人应用，再重新建设团队平台。UI 与功能一起推进，不把设计留到最后。

路线聚焦用户得到什么能力、能力依赖什么基础。产品效果、测试、质量与上线评估由内部团队安排，不在这里规定样本数量、验证指标或强制阶段审批。

## 2. 完整路线

| 阶段 | 用户获得的能力 | 主要建设内容 | 可展示的产品形态 |
| --- | --- | --- | --- |
| M0｜产品与体验样板 | 看懂最终产品如何工作 | 核心页面、组件、任务术语、继续／协助／并行交互、协议设计 | 工作台进入任务，再查看成果的可点击样板 |
| M1｜在一个任务里真正工作 | 从简短目标开始，使用 AI 并看到修改 | 账号与项目、轻量任务、本地执行器、首个工具、工作区、状态、基本代码与结果展示 | 新建任务→实际执行→查看结果→标记完成 |
| M2｜跨工具与真人协作 | 同一任务换工具、请帮忙、交给同事 | Claude Code 与 Codex、模型配置、临时协助、必要上下文、检查点接手、选择性分享 | 一人换工具与两人接手使用同一任务 |
| M3｜项目到成果的完整体验 | 组织一组工作，比较方案并呈现成果 | 需求说明、看板与依赖、团队约定、并行方案、预览与反馈、管理概览、可选检查与发布关联 | 从项目目标直接进入工作、讨论和实际成果 |
| M4｜日常使用与扩展 | 在不同环境持续使用并复用工作方式 | 远程节点、模板、有界自动化、集成、搜索、成本、维护与更多能力适配 | 完整团队工作台与可扩展执行能力 |

当前只建立文档基线；M0 的高保真原型和其余应用能力均未据此宣称完成。首个工具可以先接通一个，第二个工具仍是 M2 的核心，不是未来可有可无的功能。

## 4. 产品依赖与开发顺序

**共同基础：**先明确 Task、Run、WorkingCopy、Result 的区别，以及归属、可见范围和状态来源。界面可以使用明确标注的模拟适配器先行，但不能用模拟完成代表真实执行成功。

**核心切片：**任务入口、执行连接、代码与结果展示共同形成一条可用路径。按用户动作交付，而不是先完成所有后端再设计界面。

**接续能力：**在执行记录与工作现场基础上增加跨工具继续；在选择性分享基础上增加协助；在检查点与节点授权基础上增加跨成员接手。

**并行能力：**先有独立工作区和结果版本，再增加方案分支、对比与选择性整合。不能先多开写入进程，再补冲突边界。

**完整项目：**把资料、需求、约定与已有任务关联，管理视图直接汇总事实，不建立汇报专用状态。

## 5. UI 投入顺序

第一组重点页面是工作台、任务工作区与成果页，决定“目标—协作—结果”的整体体验。项目组织、继续／协助／并行／接手面板与核心页面同时设计。

资源设置保持清楚易用，但不先把全部投入放到插件管理、账号大屏和复杂流程编辑器。浅色与深色、不同屏宽、空状态与错误状态均使用统一组件。

新界面以产品 v1.1 行为与已确认的 [Workbench W1](../design/README.md) 为准；客户端形态见 [ADR-0008](../engineering/adr-0008-client-surfaces.md)。参考演示和 Figma 的选用内容不代表业务能力已实现。日常首页不使用品牌宣传页代替工作入口。

## 6. 自研投入与范围控制

主要自研投入为任务协作、上下文接续、跨工具动作、成果体验及统一 UI。账号、数据库、Git、终端和差异展示优先复用适合的基础组件。

模型、执行资源、服务器、存储和长期维护单独预算。具体工期取决于人员、技术栈、操作系统和接口适配，不用代码生成速度替代排期依据。

版本计划应明确本次解决的问题与投入边界。新增功能优先说明它如何减少重新解释、追问或寻找成果，而不是只说明它属于某种管理方法。

## 7. 内部评估与产品边界

如何判断阶段可以进入真实使用、怎样检查安全与性能、如何评估团队收益，由内部团队决定。通用责任说明见 [内部评估说明](../engineering/internal-evaluation.md)，不要求在 HEXU 界面里建立对应流程。

产品需要如实展示执行、权限、错误与成果；这属于功能实现，不因减少验证环节而省略。运行测试结果未产生前不能声称已经通过。
