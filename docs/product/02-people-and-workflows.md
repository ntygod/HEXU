# 02｜人、角色与协作旅程

> 规划基线 v1.1 · 2026-09-25 · 场景为虚构示例；角色不等于必须设置的岗位。  
> [返回入口](../../README.md) · [功能规格](03-functional-specification.md) · [状态规则](05-domain-and-state.md)

## 1. 人是参与工作的人，不是批准 AI 的按钮

HEXU 帮人开始、组织、理解和推进工作。人既可以委派，也可以亲自写代码、局部修改 AI 的建议、请别人帮忙、换工具或停止。保留主导权不等于所有事情都弹出确认框。

平台减少重复解释、追问和寻找成果，而不是要求每个人先学习一整套制度。普通任务从简短目标开始，复杂信息随着工作补充；测试、业务判断和产品评估由团队自行安排。

## 2. 主要角色与日常体验

| 角色 | 希望完成什么 | 产品应提供什么 | 不应增加什么 |
| --- | --- | --- | --- |
| 需求提出者、业务同事 | 把想法交给团队，看到实际结果 | 自然语言输入、截图、讨论、预览与反馈 | 完整 PRD 和正式审批的必填门槛 |
| 负责人、技术负责人 | 分工、协调依赖、处理需要决定的问题 | 轻量任务、相关提醒、团队概览与成果 | 另一份汇报表和员工操作监控 |
| 开发者 | 保留熟悉工具，连续推进工作 | 本地接入、上下文、继续、协助、并行、外部 IDE | 每次切模型都要走交接流程 |
| 协作者、内部评估人员 | 快速了解具体问题并给反馈 | 必要材料、目标版本、回应和成果入口 | 为临时帮忙强制接管整个任务 |
| 平台维护者 | 维护连接、权限和基础可用性 | 节点健康、配置、诊断与恢复 | 默认拥有别人私人电脑和全部会话的权限 |

同一个人可以承担多种角色。日常页面突出任务负责人和参与者，只有执行或分享涉及权限时才展开权限信息。

## 3. 三种人的参与方式

**负责：**对任务推进负责。创建时默认自己，也可分配给同事；AI 执行不会使真人责任消失。

**协助：**回应问题、看一段代码、补一个方案。默认不转移负责人，不要求停止整个任务，也不自动获得写入权。

**接手：**继续操作现有工作现场。需要可恢复的代码和必要信息；可以只接手操作，也可以明确接受责任转移。

管理者可看任务不等于可控制成员节点。讨论中回复“可以”不自动批准无限执行权限。成员可以按团队方式标记完成，不要求配置独立验收岗位。

## 4. 降低使用负担的默认行为

| 场景 | 产品自动处理 | 用户何时需要介入 |
| --- | --- | --- |
| 创建任务 | 带入项目、创建者、最近目录与工具偏好 | 更换归属或负责人时 |
| 开始执行 | 准备项目资料、约定和当前工作记录 | 缺少目录、工具或授权时 |
| 同机换工具 | 整理必要上下文、关联当前变更和新执行 | 原写入未停止、配置越界或材料缺失时 |
| 请求协助 | 引用选中的消息、文件或成果版本 | 选择协助者和分享范围时 |
| 同事接手 | 准备工作说明并检查可恢复条件 | 接受接手或补充缺失项时 |
| 查看成果 | 整理变更、预览与可编辑说明 | 反馈、继续或标记完成时 |

资料获取与自动处理均在已有授权内；不能用“自动化”扩大数据发送、账号使用或节点操作范围。

## 5. 九条关键用户旅程

### HX-J01｜从一句需求开始

**参与者：**业务同事、负责人。**关联：**HX-F01、F02、F03。

用户输入“后台支持按月份导出订单”，附一张示意图。系统保留原文并提供可编辑说明；字段、权限和数据量等问题以建议形式出现，不要求全部回答才能保存任务。

简单工作直接开始，复杂需求再拆分。用户可逐段采用 AI 建议，也可不使用 AI，自己写说明。没有代码仓库时仍能讨论，进入代码执行时再连接环境。

**体验目标：**把想法放进工作流，而不是先写一份完整管理文档。

### HX-J02｜从 Claude Code 切到 Codex 继续

**参与者：**开发者、两个工具。**关联：**HX-F04、F05。

开发者已经使用 Claude Code 完成部分修改，选择“用 Codex 继续”。原写入已结束且在同一电脑时，系统带入目标、约定、当前变更和剩余问题，选择有效配置后启动新 Run，仍属于原任务。

界面简短说明使用当前目录及新会话，详细上下文可以展开修改。不要求每次保存为正式交接包或向远程仓库推送提交。

原执行仍在写入时，先请求停止并等待实际确认；换电脑时则走检查点恢复。目标工具不支持某能力时说明替代方式，不假装原生会话已完整迁移。

**体验目标：**换执行工具，而不是从头解释工作。

### HX-J03｜两位成员并行推进相关任务

**参与者：**负责人、前后端开发者及各自 AI。**关联：**HX-F03、F06、F08。

负责人安排前后端工作，使用一条简短接口约定连接任务。两位开发者保留自己的工具与环境，通过独立工作区推进。

接口字段需要调整时，成员在相关任务里讨论；有权限者直接“设为项目约定”。平台提示相关人员，并说明当前执行是否已经收到变化。普通改动不自动触发多级审批或冻结所有任务。

**体验目标：**知道对方在做什么，重要变化及时进入相关工作，而不是共享所有私人聊天。

### HX-J04｜同事接手未完成工作

**参与者：**交出者、接手者。**关联：**HX-F06、F11。

交出者点击“交给同事”，系统整理工作说明、代码检查点和环境要求。跨电脑需要让接手者可以访问实际代码，而不是只发送摘要。

接手者查看概要并点击接手；系统自动检查权限和现场，仅对缺工具、缺文件等问题展开提示。默认改变当前操作者，责任人是否一并转移在同一界面明确选择。

原电脑失联且没有足够检查点时，展示可恢复范围；不把接手按钮变色当作已接管进程。个人凭证不跟随任务转移。

**体验目标：**减少重讲与重复探索，但只为真实缺失项打断用户。

### HX-J05｜临时请人或 AI 协助

**参与者：**当前开发者、同事或另一 AI。**关联：**HX-F05、F06。

开发者选中报错、代码片段或设计说明，点击“请协助”，指定问题和接收者。系统带入所选材料与版本，而不是整个私人会话。

同事可以直接回复；另一个 AI 在只读范围或隔离副本提出建议。原任务继续由当前开发者负责，不因请求帮助就更换负责人或中断所有工作。

开发者采用、局部修改或忽略建议。需要协助者真正改代码时，再明确进入并行分支或接手。

**体验目标：**低成本增加一个参与者，而不是转交一项完整工作。独立代码审阅是其中一种用途，不是每项任务的必经环节。

### HX-J06｜业务同事查看成果并反馈

**参与者：**开发者、业务同事或负责人。**关联：**HX-F09、F10。

开发者分享订单导出页面预览、样例文件与简要说明。业务同事直接看到结果，评论“按钮放到筛选栏右边”。反馈留在原任务，可继续修改或生成后续任务。

团队按自己的方式判断后标记完成，无需创建标准验收清单或上传报告。已有测试、检查记录与发布链接可以作为附件保留，不强制采集。

任务完成、AI 执行结束和实际上线分别显示。后续需要修改时直接重新打开，不因为新评论就自动重置历史完成。

**体验目标：**看见结果并参与改进，而不是填写一份验收档案。

### HX-J07｜节点离线，稍后继续

**参与者：**开发者、维护者。**关联：**HX-F04、F11。

节点离线后任务页保留最后已知内容，显示连接未知与最后确认时间。用户可以查看已有成果和讨论，不需要整个工作台一起不可用。

节点恢复后系统核对原进程、当前变更和事件，提供继续或处理异常的入口。未知的外部操作不自动重试；原写入未确认结束时不能启动同现场另一个写入者。

平台服务不可用时，本地代码仍可使用；恢复后标记可识别的外部变化，不声称完整追踪离线行为。

**体验目标：**故障可以理解和恢复，不丢失工作方向，也不制造虚假的完成。

### HX-J08｜管理者快速了解项目

**参与者：**管理者、负责人。**关联：**HX-F03、F09、F10。

首页显示当前目标、正在推进的工作、等待自己回复的问题与近期成果。管理者打开“导出字段范围待回复”，直接在相关任务回应；随后进入最新预览查看结果。

不需要看全部终端，不需要开发者额外填写汇报。任务计数标明口径，没有依据不显示精确进度百分比或预测日期。成员页展示负责事项与协助入口，而不是在线时长排行。

**体验目标：**从目标到具体工作再到成果，能直接采取行动。

### HX-J09｜比较两个方案，再选一个继续

**参与者：**开发者、两个工具或成员。**关联：**HX-F05、F07。

用户为同一任务创建两个方案分支，例如两种导出实现方式。系统展示各自范围、共同起点和独立工作区，分别执行并保留结果。

用户对比代码、说明和预览后选择一条继续，或选择性整合。另一方案保留历史，可单独停止或归档，不自动把所有修改混在一起。

分支增加的执行资源与可获得的费用信息可见；默认不启动无限 Agent 竞赛，也不自动给方案排出“绝对最佳”。

**体验目标：**看清选择，而不只是管理更多窗口。

## 6. 私人探索、共享与注意力

私人探索默认不进入团队进度。转团队时选择需求说明、变更、约定和必要记录，不自动公开全部终端、环境变量和历史会话。管理设备是否存在额外管理权限，在接入时说明，不能承诺绝对私密。

提醒跟随问题与参与者：提及、协助、接手、反馈和必要授权优先；普通进展可以摘要。同一原因合并，不把每个 token、工具调用和文件修改都变成通知。

看到通知不等于接受责任，回复意见不等于接受接手，点击完成不等于批准部署。底层区分保留，普通界面不强迫用户学习全部术语。

## 7. 团队评估边界

如何访谈、比较效率、测试质量、选择评估人员与决定何时上线，由内部团队安排。HEXU 提供可用的任务、讨论、成果和必要日志，不把这些评估方法自动开发成新的必填页面或流程。
