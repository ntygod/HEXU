# 02｜人、角色与协作旅程

## 1. 先设计人的工作，而不是 Agent 组织架构

HEXU 要解决的是工作连续性，不是要求每个团队先创建一群具有职级和人格的虚拟员工。

人应保有选择、理解、干预和拒绝的能力。AI 可以提出方案、执行任务、协助审阅，但它的输出不能自动取得人类批准的权威性。

“减少人的操作”不等于“减少人的控制”。好的自动化应减少重复填表和等待，而不是让用户为了恢复控制去阅读几千行日志。

## 2. 关键使用角色

| 角色 | 想完成的事情 | 主要阻力 | HEXU 的关键支持 |
| --- | --- | --- | --- |
| 需求提出者／业务人员 | 把想法变成可以检查的结果 | 不知道怎样写完整需求；不理解代码状态 | 原始输入保留、关键问题确认、预览与验收项 |
| 负责人／技术负责人 | 组织分工、处理依赖并承担交付 | 进度靠追问；决定分散；责任不清 | 真人责任人、依赖、决策队列、交接与交付视图 |
| 开发者 | 高效解决问题，保留熟悉工具 | 切换成本、重复背景、环境差异、额外管理负担 | 私有探索、工具选择、检查点、外部 IDE 与任务关联 |
| 审阅／验收人员 | 判断结果是否符合要求 | 不知道测哪个版本；缺少复现条件 | 固定版本、验证证据、预览、接受／退回与理由 |
| 平台维护者 | 让系统可靠、成本和权限可控 | 版本不兼容、节点掉线、凭证和日志敏感 | 健康诊断、能力矩阵、权限、审计、备份与恢复 |

管理者通常属于前两类；不是一个默认拥有所有电脑和私人会话访问权的超级用户。

## 3. 四种权限不能混为一谈

**可见权：**可以查看哪些任务、会话片段、产物和费用。

**操作权：**可以启动、干预和停止哪些执行，能否使用某个节点。

**决策权：**可以确认需求、扩大范围、修改团队约定或批准特定操作。

**验收与发布权：**可以接受哪个版本的成果，是否可以发布到指定环境。

团队管理员负责账号与配置，不自动获得成员私人执行节点的控制权。节点所有者授权只说明可以使用该节点，不代表可以访问节点之外的仓库、密钥或生产系统。

### 建议的责任分配

| 动作 | 谁最终负责 | AI 可以做什么 | 不允许的替代 |
| --- | --- | --- | --- |
| 确认需求 | 指定需求确认人 | 提取信息、指出歧义、给出选项 | 把推测改成已确认事实 |
| 承诺交付和分工 | 任务真人责任人 | 规划、估算、发现依赖 | 将责任移交给一个 Agent 名称 |
| 执行变更 | 具备操作权的执行者 | 在范围和策略内编辑、测试 | 借其他 Agent 权限执行被拒绝操作 |
| 扩大权限 | 对相应资源有授权权的人 | 说明理由和影响 | 从聊天中的“可以”推断无限权限 |
| 接受结果 | 指定验收者 | 总结变更、列出风险与证据 | 自己声称完成即通过验收 |
| 发布 | 指定发布者或已批准的发布策略 | 执行检查与部署步骤 | 把合并代码等同于上线成功 |

低风险任务允许一人兼任多个角色，但界面和审计记录仍区分各动作。高风险项目可以要求审阅与实现分离，是否启用由项目策略明确。

## 4. 人的隐私、注意力与采用成本

### 4.1 私有探索与团队工作分离

个人探索默认不在团队进度里展示。发布为团队任务时提供共享预览，逐项选择需求说明、变更、决定和必要记录。不自动上传全部终端、环境变量、私人笔记或历史会话。

在公司管理设备和账号上的数据是否存在管理访问权限，必须在接入时明确告知；“默认不在团队界面公开”不能表述成法律或技术意义上的绝对私密。

正式任务中的共享决定与交付依据应留存，私人探索与审计记录使用不同保留规则。

### 4.2 只打扰需要采取行动的人

按任务负责人、验收者、资源授权者路由消息。同一原因产生的多条提醒合并；例行进展可以摘要，阻塞、授权和验收形成可处理事项。

提醒必须回答：为什么找我、影响什么、我能做什么、不处理会怎样。阅读通知不等于已接受决定；确认收到不等于相关运行已更新上下文。

### 4.3 不新增一份汇报工作

从真实任务、Git 和验证记录自动汇总进展。系统不知道的部分显示未知，不让开发者为了保持首页好看而手工填虚假百分比。

保留直接打开 IDE、终端和原生工具的入口；逐步接入团队需要的部分，不要求导入所有历史工作。

### 4.4 让人能解释和纠正系统

所有 AI 整理、冲突建议、路由和风险摘要都有来源与纠正入口。用户可以拒绝建议、暂停自动化、请求人工帮助；纠正不会删除此前的关键执行证据。

## 5. 八条关键用户旅程

所有场景均为虚构，用于设计与验证，不是已发生的客户案例。

### HX-J01｜从一句需求开始

**参与者：**需求提出者、负责人。 **关联：**HX-F01、F02、F03。

用户输入“后台需要按月份导出订单”，附上示例。系统保留原始文本，建议结构化目标、范围和验收项，并提出权限、字段与大数据量处理等关键问题。

确认人只需要处理真正影响实现的歧义；未确认的推测保持标记。确认后产生需求版本，责任人接受任务或调整计划。没有仓库时仍可讨论和规划，执行前才引导连接仓库。

**成功：**参与者对要做什么、哪些不做、如何验收有一致记录。

**异常：**确认人缺席时保持待确认；不能由 AI 因等待超时自行批准。原始需求变化需产生新版本及影响提醒。

### HX-J02｜个人在两个工具之间接力

**参与者：**一位开发者、Claude Code、Codex。 **关联：**HX-F04、F05、F06。

开发者先用一个工具分析和实现，决定换工具继续时，系统检查原运行是否结束、工作目录是否有未保存变更、代码基线是否一致。

系统生成可编辑交接包；用户确认共享给新工具的内容、模型、执行位置、数据范围与预算。新工具拿到代码检查点、必要背景与未完成事项后启动新 Run，仍属于原 Task。

**成功：**新工具恢复工作，不重复已经解决的关键问题；原工具不再与它同时写入同一现场。

**异常：**只有聊天摘要、缺少代码时不能显示“接力就绪”；模型额度不足时建议备选，不自动使用未授权付费账号。无法停止原运行时阻止共享工作区接管，允许另开隔离副本调查。

### HX-J03｜两位成员并行开发

**参与者：**负责人、前后端开发者、各自 AI。 **关联：**HX-F03、F06、F08。

负责人确认接口约定版本，前后端任务分别持有输入、输出与依赖，开发者在独立工作区执行。

后端提出字段调整时，先形成变更建议。确认后平台标记依赖任务受影响，前端负责人处理变化，其运行记录保存接受的新上下文版本。

**成功：**并行工作在正确前提下集成；原验收证据不会被沿用到不匹配的版本。

**异常：**文件没有重叠仍可能存在语义冲突；系统提示只是风险线索，最终由接口检查、集成测试和人员判断确认。

### HX-J04｜把未完成工作交给同事

**参与者：**交出者、接手者、真人责任人。 **关联：**HX-F06、F11。

交出者请求停止或完成当前写入，发布经检查的 Git 检查点与交接包。接手者检查仓库权限、可用环境、未包含文件、运行方式和未解决问题，然后确认接受。

默认只转移“当前操作者”；需要转移“真人责任人”时另行明确确认。原个人凭证不会随任务转交。

**成功：**接手方能独立恢复工作，交接过程可追溯；没有两个执行者误以为自己拥有同一工作区。

**异常：**接手者无权限或环境缺失则交接保持未接受；原电脑离线且没有检查点时，只能说明可恢复范围，不能伪装无缝接手。

### HX-J05｜实现与独立复核

**参与者：**开发者、实现 Agent、复核 Agent、审阅者。 **关联：**HX-F05、F07、F09。

实现 Agent 提交固定版本，另一个 Agent 在只读或隔离环境中检查明确风险，例如并发、权限或兼容行为。审阅者依据复核结论和真实测试决定处理方式。

**成功：**每个问题能定位到版本和证据；修复后原复核结果被标记需更新。

**异常：**复核 Agent 与实现 Agent 观点冲突时，由人裁决或增加验证；不能把“两个模型同意”作为通过依据。自动修复循环达到上限时停止并解释。

### HX-J06｜业务人员验收并发布

**参与者：**验收者、审阅者、发布者。 **关联：**HX-F09、F10。

验收页提供受保护的功能预览或样例产物、需求验收项、测试结果和已知风险。验收者逐项确认或退回，系统记录针对哪个需求与代码版本的决定。

代码接受与发布批准分别进行。发布结果由真实部署记录或明确的人工记录确认；失败时保留已验收事实和发布失败状态，不互相覆盖。

**成功：**从需求可以找到结果、证据、验收者和发布位置。

**异常：**预览失效不假定功能失败也不显示通过；发布后数据问题不能用“Git 回滚”伪装已恢复，需要独立恢复方案。

### HX-J07｜节点离线或执行失联

**参与者：**操作者、维护者。 **关联：**HX-F11、F10。

平台失去心跳后显示“状态未知”与最后确认时间，而不是继续运行或自动失败。节点恢复后核对原进程、事件序号和工作区状态，再决定继续、终止或人工介入。

**成功：**不丢失已持久化信息，不重复部署、提交或外部写入，不让旧事件覆盖新状态。

**异常：**无法确认原写入停止时，不给另一个进程同现场写入许可。中心服务不可用时，用户仍可本地工作；恢复后将外部改动作为待核对变更处理。

### HX-J08｜管理者处理例外而不是监控所有人

**参与者：**管理者、负责人。 **关联：**HX-F10、F02、F09。

首页显示“订单导出等待字段确认”“新预览可验收”等有上下文的事项。管理者进入具体任务作出决定、查看实际成果，而不需要研究所有会话。

**成功：**能回答目标、阻塞和成果；处理决定能回到相关任务与执行。

**异常：**缺少估计或验收依据时显示缺失，不生成精确百分比或完工日期；不按 Agent 数、token 或在线时长对人排名。

## 6. 首次使用与渐进规范化

首次进入先允许创建一个需求或探索任务，再引导必要的项目和节点配置。接入只读代码分析可以作为低风险起点，但正式写入必须先说明权限与数据范围。

基础模板帮助用户确认目标、边界、验收，不要求填写长篇材料。规则分三个层级：个人探索的最小记录；团队任务的责任与交接；高风险变更的授权与独立验收。

团队采用过程应观察哪些操作减少了沟通，哪些只是转移了填表成本。新增必填项必须有明确的风险或验收理由。

## 7. 使用者研究方法

观察真实任务如何开始、切换、交接和验收；优先让成员展示最近的一次失败或重复解释，不只询问他们是否喜欢某个功能名称。

访谈需要覆盖需求提出者、至少两名使用不同工具的开发者以及验收者。收集前说明数据范围，避免上传客户信息、凭证和完整私人会话。

研究输出是断点、频率、人工耗时、现有解决办法与产品新增负担。未经验证，不把访谈个例写成普遍规律。详细指标和试点设计见 07。
